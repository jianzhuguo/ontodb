## 场景2：本体内核化原理（0:30-2:30）

### 问题引入（0:30-1:00）

### 画面
- 传统架构图
- 性能瓶颈动画

### 旁白
```
传统方案将推理引擎作为独立组件部署。
数据从存储引擎到推理引擎需要：
序列化、网络传输、反序列化、执行推理、再返回。

这个过程的延迟超过100毫秒。
```

### 解决方案（1:00-2:00）

### 画面
- OntoDB架构图
- 共享内存动画

### 旁白
```
OntoDB的解决方案是：将推理引擎直接嵌入数据库内核。

存储引擎和推理引擎共享同一块内存空间。
数据无需序列化、无需网络传输、无需反序列化。

推理过程直接访问内存中的数据，延迟降到1毫秒以内。
```

### 代码演示（2:00-2:30）

### 画面
- 代码动画
- 执行流程动画

### 旁白
```
让我们看看代码实现：

StorageEngine结构体包含memtable和inference_engine。
写入数据时，直接调用inference_engine.incremental_reason()。
推理结果直接写入memtable，无需任何中间转换。

这就是"本体内核化"的核心原理。
```

## 场景3：增量推理原理（2:30-4:00）

### 问题引入（2:30-3:00）

### 画面
- 全量推理vs增量推理对比
- 性能对比图表

### 旁白
```
传统推理引擎每次都需要全量扫描所有数据。
数据量越大，推理越慢。

OntoDB采用增量推理算法：
只对新增或变更的数据执行推理规则。
```

### 算法原理（3:00-3:30）

### 画面
- 增量推理算法动画
- 工作队列动画

### 旁白
```
增量推理算法使用工作队列：

1. 将新增数据加入工作队列
2. 从队列取出数据，执行推理规则
3. 将推导结果加入队列
4. 重复直到队列为空

这样，只有变更的数据会被处理，大幅减少推理工作量。
```

### 性能对比（3:30-4:00）

### 画面
- 性能对比图表
- 延迟对比动画

### 旁白
```
性能对比：

批量推理1000条数据：
- 传统方案：15秒（全量推理）
- OntoDB：12毫秒（增量推理）
- 提升：1250倍
```

## 场景4：统一标识原理（4:00-5:30）

### 问题引入（4:00-4:30）

### 画面
- 映射表架构图
- 查询流程动画

### 旁白
```
传统多模态数据库需要维护映射表。
每个实体需要记录它在各存储引擎中的ID。

跨模态查询时，需要先查映射表，再查各引擎。
这个过程的延迟超过50毫秒。
```

### 解决方案（4:30-5:00）

### 画面
- 统一标识架构图
- 查询流程动画

### 旁白
```
OntoDB的解决方案是：统一标识。

统一标识格式：{类名}::{主键}
例如：Device::001

这个标识同时作为：
- 结构化记录的主键
- 图结构的顶点ID
- 向量索引的文档键
- 语义三元组的主体
```

### 性能对比（5:00-5:30）

### 画面
- 性能对比图表
- 查询延迟对比动画

- OntoDB：3毫秒（统一标识直接查询）

## 场景5：写入联动原理（5:30-7:00）

### 问题引入（5:30-6:00）

### 画面
- 传统写入流程动画
- 数据不一致问题动画

### 旁白
```
传统方案写入后需要异步同步。
数据写入MySQL后，需要ETL同步到Neo4j和InfluxDB。

同步延迟从秒级到分钟级。
在这个时间窗口内，数据是不一致的。
```

### 解决方案（6:00-6:30）

### 画面
- 七步联动管线动画
- 三阶段锁动画

### 旁白
```
OntoDB的解决方案是：写入联动。

在单一事务中原子完成七步操作：
1. 写入结构化数据
2. 创建图顶点
3. 生成类型三元组
4. 生成属性三元组
5. 执行增量推理
6. 更新向量索引
7. 更新辅助索引

使用三阶段锁保证原子性。
```

## 场景6：活数据原理（7:00-7:30）

### 画面
- 价值衰减曲线动画
- 自动激活动画

### 旁白
```
OntoDB的活数据机制，让数据像人类记忆一样衰减。

每条数据维护价值指标，随时间指数衰减。
数据被访问时自动激活，重置衰减时钟。

这样，热点数据自动优先展示，冷数据自动降级存储。
存储成本降低60%。
```
