# 2026-11-19

## TCP 行读取改为有界（1MB 上限此前不是硬流控）

- 问题：`handle_client` 用 `AsyncBufReadExt::read_line` 把整行攒进 `String` 后才检查 `line.len() > MAX_LINE_BYTES`。客户端不发换行时可无限增长缓冲区，上限只是事后拒绝，内存已经吃掉。
- 修复（`crates/onto-server/src/main.rs`）：
  - 新增 `read_line_bounded()`：用 `fill_buf`/`consume` 按块读取，在**拷贝前**判断是否会超过 `max_bytes`，超出立即停止累积。
  - 新增 `drain_to_newline()`：超限后以常量内存丢弃到下一个换行，使流重新对齐到查询边界；丢弃量超过 `MAX_DRAIN_BYTES`（8MB）则返回 `Aborted` 并断开连接。
  - `LineRead` 四态：`Line` / `Eof` / `TooLong`（已重同步，回错后可继续）/ `Aborted`（无法重同步，断开）。
  - `handle_client` 循环改用新函数；非 UTF-8 不再断连，改为回 `ERR: query is not valid UTF-8` 后继续。
- 测试（`#[cfg(test)] mod tcp_line_tests`，5 个）：
  - 多行正常读取、末尾无换行的部分行 + EOF、超长行（2MB 无换行）缓冲不超 cap 且能重同步、整行落在一个 chunk 内超限、无换行无限流返回 `Aborted`。
- 端到端验证（真机 server，端口 17913，独立数据目录）：
  - 发 2MB 无换行 + 换行 → `ERR: line too long (max 1MB)`，随后 `SHOW CLASSES` 仍返回 `(0 rows)`，连接可继续用。
  - 发 16MB 无换行 → 客户端在第 9,895,936 字节被断开，服务端日志 `oversized request with no newline, closing`；约等于 1MB cap + 8MB drain budget。

编译验证注意：仓库快照仍缺 `crates/onto-{sharding,raft,enterprise}` 与多个 `tools/*`。验证时临时建空占位 crate（`onto-enterprise` 需补 `encryption`/`audit-retention`/`enterprise-standard`/`enterprise-gov` 空 feature）并缩减 workspace members，结束后已全部恢复。

## Review 后追加的改进

- `max_drain` 参数化（原先硬编码 `MAX_DRAIN_BYTES`，测 `Aborted` 要分配 8MB）。
- 错误消息改为按 `MAX_LINE_BYTES` 计算 MB 数，不再写死 `"1MB"`。
- 新增 `overflow_after_large_prefix_keeps_buffer_bounded`：用 `BufReader::with_capacity(1024)` 让前缀真正进入 `buf` 后再溢出，原用例首 chunk 即超限、`buf` 从未 extend，断言恒真。测试共 6 个。
- 已知未处理：无读超时（慢速无换行流仍可长期占用连接槽，建议加 `tokio::time::timeout`）；Vec 倍增使实际上界约 2×cap；`mem::take` 每次丢容量。
